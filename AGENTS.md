# Rules for Agents 
 
1. Anti-sycophancy. Never say "you're absolutely right" or even mild praise.
2. Anti-personality. It's weird for a coding agent to use first-person pronouns. Better to write everything completely passively/dispassionately referring to what "Fable" or "Sol" or whatever model it is is doing. Except when active voice adds clarity. And sycophancy-adjacent filler like "deserves a straight answer" should die in fire. Jump straight to answers, zero preamble.
3. Anti-info-dumping. Ask clarifying questions one at a time or give a numbered list.
4. Red/green QDD. I.e., TDD except we [call them quals](https://blog.beeminder.com/quals "Beeminder blog post about why to prefer the term 'quals' to 'tests'; the term 'specs' would be pretty good too"), not tests. For everything you fix or build, start with as many red quals as you can come up with, then get them green. 
5. Quals are sacred. Treat quals as a functional spec for the implementation to conform to. Discuss any spec change with the humans.
6. Prose persnicketiness. Human-written comments or UI/microcopy is sacred. LLMs (at least older ones?) tended to slightly rephrase text when copying it. Not ok! Preserve the exact characters, even whitespace, in any English text.
7. Latin microcopy. When generating new UI copy, error copy, help text, even microcopy like text on buttons -- any words the end user is intended to read -- write it initially in Latin. The idea is that the end user never reads any English text that was generated by an LLM. If the human's spec specifies exact copy you can of course use that, but see the previous rule about preserving exact characters. Either way, add a comment in the code right above the Latin with "TO-DO" (except without the hyphen) and a recap of what the UI copy is meant to convey.
8. Beeminder's [Pareto Dominance Principle (PDP)](https://blog.beeminder.com/pdp "Not to be confused with the Pareto Principle aka the 80/20 rule "). Get explicit approval if any change would deviate from the Pareto frontier. Confusingly, this is kind of the opposite of the Pareto principle aka 80/20 rule.
9. Beeminder's [Anti-Magic Principle](https://blog.beeminder.com/magic "An extreme version of this is worse-is-better where code elegance and simplicity is prioritized over correctness; but coding agents shouldn't try to make judgment calls like that"). "If-statements considered harmful." Minimize cyclomatic complexity. If you're fixing a bug like "when X happens the app does Y instead of Z", resist the urge to add "if X then Z" to the code. Fastidiously mention every if-statement you think you need. Constant vigilance to minimize code paths! When we do add an if-statement aka a branch in the logic (again, don't assume we should) minimize the difference between the branches, i.e., change the program's behavior as little as possible. Like add an error banner if there's an error rather than rendering a different page. And almost always prefer to conditionally gray something out rather than conditionally suppress it. We can't overemphasize anti-magic enough. We've yet to find the limit beyond which being more dogmatic about it stops bearing fruit.
10. Code smells. Follow all the standard principles like DRY and YAGNI and ZOI (Zero-One-Infinity) and KISS and SPOT. Not POLA though; anti-magic trumps that one. And no DWIM; anti-magic means anti-DWIM. (Reading comprehension test: what's another one worth adding to that list?)
11. Beeminder's [Anti-Settings Principle](https://blog.beeminder.com/choices "AKA Choices are Bad"). Not that a coding agent would add settings without asking, but it's a good principle to have in mind in planning mode.
12. Beeminder's [Anti-Robustness Principle](https://blog.beeminder.com/postel "Make your code overly literal and punctilious and pedantic and simplistic, making zero assumptions about intent") aka Anti-Postel. Fail loudly and immediately. Never silently fix inputs. Instead of "fallback handling", do asserts that force a crash. In fact, use asserts everywhere you can think to. See also the branch of defensive programming known as offensive programming. Anti-robustness is huge, on par with anti-magic.
13. Nominology/[Neology](https://blog.beeminder.com/neology/ "As in coining neologisms"). Decades ago programmers became infamous for opaque variable names and they've been overcompensating almost as long. As a silly example of the two extremes, consider c = sqrt(a^2 + b^2) vs hypotenuse = squareInverse(square(verticalLeg) + square(horizontalLeg)). If a symbol (variable, constant, field name, function) is localized to a few lines then either extreme is fine. Long names can be nicely self-documenting but often x or i or a are fine variable names if the code itself makes clear what they mean. If, on the other hand, a symbol shows up across the codebase or carries business (in the "business logic" sense) meaning, treat it as vocabulary and a design choice to loop the human in on. Ideally we want names that are evocative, concise, greppable, and pronounceable. (Whoever came up with "sqrt" did this perfectly. It's ubiquitous enough that it's worth abbreviating, and can be pronounced as "square root" or "squirt".) Think of the name as jargon, in the positive sense, and never use [pseudovernacular jargon](https://blog.beeminder.com/pseudovernacular "Beeminder blog post railing against this; mathematicians are the worst of all with things like 'real' and 'natural' and 'normal' and even 'onto' and 'almost surely'; the problem is when you *don't know that you don't know* what the words mean"). Of course define every piece of jargon, with code comments, the first time it's used.
14. Replicata/Expectata/Resultata. Those are the three parts of a [proper bug report](https://blog.beeminder.com/bugreports "Beeminder blog post about how users talk themselves out of reporting bugs, but the relevant part is the definition of a proper bug report"): (1) steps to replicate the bug ex nihilo, (2) what you expected to happen, and (3) what happened instead. A failing qual should also be framed that way.
15. Git off my lawn. My workflow is to always stay on the main/master branch, let the AI make edits, review those in my IDE, and then manually, as the human, type a commit message and push and sync to master. So you, the AI, can use read-only commands like git diff and git log as needed but no mutating git commands. Those break my workflow. (This should be enforced directly in settings.json too; please confirm.)
16. Relatedly, do dev work in this repo's working directory where the human can watch in the IDE. Exploratory work can go in a scratch directory, which you can git-ignore.

Recap: Anti-sycophancy, anti-personality, anti-info-dumping, QDD, quals are sacred, prose persnicketiness, Latin microcopy, PDP, anti-magic, code smells, anti-settings, anti-postel, nominology, proper bug reports, and git workflow.

## Experimental

0. No LLM-isms, no sentence whose only job is rhythm or closure.
1. It's ok to say "I don't know".
2. Provide primary sources for research.
3. DataColada/Gelman rigor, not textbook consensus.
4. Math/natural science: 3Blue1Brown and David Deutsch hold the standard for lucid, penetrating explanation.
5. Scott Alexander's compendious dispassionate epistemics, just needs to be condensed into succinct prose.
6. Epistemic humility. Before finalizing your response, ask yourself if it's impeccably, exquisitely, technically correct and true.

## Cutting Room Floor

I'm tentatively retiring the following rules that seem unncessary for Fable and Sol. But they're still correct:

1. Empiricism. Never claim a bug is fixed or that the code exhibits some behavior without trying it.
1. Quality assurance. The human is not your QA person. Iterate on your own until your code works.
1. You can do it, agent! You are wise and thoughtful and pragmatic and only the best kind of lazy and you abhor code smells. I believe in you! Still zero personality though, please.
1. We like the anti-magic extreme of [worse-is-better](https://en.wikipedia.org/wiki/Worse_is_better "Roughly this means prioritizing code elegance and simplicity over correctness") aka New Jersey style, but knowing when to deviate from the MIT approach is something of an art and requires discussion.
1. Anti-magic covers this but it's not getting through so let's try it again. AI coding agents (pre-Fable?) seem to have an overwhelming instinct to be like "oh, thing X happens that shouldn't? or thing Y should happen? let me slap on some code to handle those cases". Instead, I beg you, think: "let me get my head around this and try to solve it by rethinking and simplifying so we don't have to reason about separate cases".

## Notes from the session that built svenn (Opus, 2026-10-06, Claude desktop app in a cloud workspace)

What it is: svenn.dreev.es, one drawing of a simple symmetric n-Venn diagram for each prime n with a known one, 3 to 23. A static page (index.html) served by GitHub Pages from main, root; CNAME and .nojekyll in the repo; DNS is a Namecheap CNAME record, host svenn, value dreeves.github.io.

Files:
* quals.py: the functional spec. `python3 quals.py` runs them all, `python3 quals.py cert svg` only those whose names contain a given word. Its docstring defines the jargon (label, face, cert).
* venn.py: `python3 venn.py certs` writes certs/venn-NN.json (gitignored). n = 3 to 13 are generated from the crossing sequences (xseq, alpha; defined in its docstring) published by Mamakani and Ruskey; n = 17 and 19 are downloaded from dzoba/venn17, pinned to commit e89d6f6 and checked against SHA-256 (they are the two Lean-verified ones). `python3 venn.py draw [N ...]` writes img/venn-NN.svg and .png.
* geom.py: sampling of cubic Beziers and segment intersection, shared by the drawing code and the quals.
* vendor/venn17: Dzoba's plotter and the modules it imports, byte-identical to dzoba/venn17 at e89d6f6 (MIT).
* tools/svg2png.mjs: SVG to PNG with @resvg/resvg-js; `cd tools && npm ci` first.
* sourcery.html: this session's transcript, made with beeminder/sourcery 5.5.0 unmodified (see Sourcery below).

Requirements: python3 with numpy and scipy, node.

## Notes from the second session (Opus, 2026-10-06 evening, VS Code on dreeves's Mac: 16 GB, 10 cores)

The viewer, view.html?n=N, is where every card with this site's own drawing links. It fetches img/venn-NN.svg (showing the card's PNG until then) and turns the file's rotated uses into one plain path per curve. The page fits between the controls along the top and the swatches along the bottom. A drag, pinch or wheel only moves the picture already drawn, with a CSS transform on the div #picture that holds the SVG; 150 ms after the view keeps still, redraw() sets the viewBox and draws it anew. Lines keep their fit-view width with vector-effect: non-scaling-stroke, which is essential, not cosmetic: with ordinary strokes a redraw of 17 at high zoom took 0.7 to 2.6 s in Chromium and Firefox. Swatch k shows curves 0 to k (dreeves's design: one curve, then add the others one at a time).

Each drawing's SVG holds curve 0 once, <defs><path id="curve">, and draws curve i as <use id="curve-i"> of it rotated about the page centre by a multiple of 360/n degrees (venn.py's compact(); 19 went from 62 MB to 4.3, with six decimals). compact() asserts first that every curve the drawer made is such a rotation to within the rounding, and qual_svg_symmetric checks the structure exactly.

Things that may trip up the next instance:
* The browser quals: quals.py runs tools/browser_quals.mjs once (cached in `_browser`) and gives each of its checks its own qual. It uses the Playwright pinned in tools/package.json, 1.61.1, because that is the version whose WebKit 2311, Chromium 1228 and Firefox 1532 builds are in ~/Library/Caches/ms-playwright on this Mac; elsewhere run `npx playwright install` in tools/. It serves the repo itself on a random port. For ad hoc servers pick a free port too: once port 8731 was taken, Python's http.server failed to bind with its output sent to /dev/null, and the requests went to the other server and got 404s.
* Viewer cost, headless, served locally (ms per redraw): 17: Chromium 16-33, WebKit 52-97, Firefox 29-110; 19: Chromium 70-130, WebKit 215-370, Firefox 120-400, the same whether the curves are paths, rotated uses or paths with a rotate transform (within noise; Firefox drew uses somewhat slower). Moving the drawn picture by a CSS transform instead costs 17 ms in Chromium and 31-44 in WebKit, but in Firefox only a translation is cheap (17 ms): scaling it costs 335 ms, more than a redraw, and transforming the SVG element itself rather than a div re-renders it in Firefox every time. A benchmark once showed 17 ms for every variant in every engine; its paths had NaN coordinates (a regex matched the "e" of "rotate") and drew nothing. Check that a fast variant draws something.
* n = 19 was first drawn here: 51 minutes wall, 19 of CPU, held back by swap (the RAM was taken by Chrome, VS Code, a VM and headless browsers); four smoothing checks (66,924, 10,925, 496, 0). That 62 MB SVG is in git history (commit f2d41cf, pushed). Compacting it (curve 0 plus rotations) gave 38 extra crossings, 2 per sector: somewhere two curves pass within about 0.001 units, and rotating rounded curve 0 moves points up to 0.0014 from where rounding each curve puts them. So smooth() now checks the curves as stored(), i.e. as the compact file holds them. Drawn again that way at three decimals, 19 still had 20 crossings wrong after eight smoothing attempts: those arcs were already straight, and straight arcs of different curves pass closer than the rounding. The plotter's drawings now give coordinates to six decimals (venn.py's DECIMALS), and 19 was drawn a third time. qual_svg_matches_cert takes 7 minutes and 3.0 GB on 19.
* The old qual_svg_symmetric (sampled distances) failed at 19 although the drawing was symmetric: its tolerance assumed geom.sample's spacing never exceeds `step`, but samples are evenly spaced in t, and on a span whose tension was cut to 0 (P1 = P0, P2 = P3) the speed is 6t(1 - t) times the chord, so the spacing reaches 1.5 times the average. Comparing control points directly showed every curve an exact rotation of another (worst 0.0014 units, from n = 7 some traced backwards), which is what compact() now asserts.
* Two adversarial reviews (workflows of four reviewers, each with a skeptic) found real problems both times; the second found mostly quals that passed with the feature broken (now each such mutation fails a qual). Worth repeating after any big change. Lessons from them: the viewer's picture must keep an identity transform, not none, or WebKit stalls 115-140 ms at the start of every gesture at n = 19; hover styles only under (hover: hover), or a tap leaves them on; qual_svg_symmetric parses the whole tree, because counting tags let black-filled and displaced curves through; the browser quals abort Google Fonts, which nothing depends on and which made every check wait.
* Layout decisions dreeves left to the agent (2026-10-07): in a landscape window the swatches stand in a column at the right edge (a flex row in writing-mode: vertical-rl, because a CSS grid column that wraps sizes wrongly in Firefox); the drawing is never under half the window's shorter side; no overscan (the blank bands a long drag reveals fill in at the redraw, as in map viewers; overscan made redraws 1.5 times slower); touch-size controls under (any-pointer: coarse); a note (#slow) while gesture frames take over 250 ms, which in practice is Firefox zooming 19.
* Browser quals: Playwright's hasTouch makes (pointer: coarse) match in all three engines. Playwright's Firefox drops mouse events outside the window, so drags in checks must stay inside it. Browsers report a wheel's clientX/clientY in whole pixels (truncated), so aim wheel checks at whole pixels. The quals' file server answers only the content types it knows (add one for a new file extension, as for site.css).
* The Edit tool sometimes drops a trailing space at the end of new_string. dreeves's prose lines end with one, so check `git diff | cat -e` after editing them.

Fact-check, done with primary sources (scans, Crossref, the papers) and two skeptics per finding; what the page now says is right as far as they could tell. Not obvious: the Ruskey-Weston survey and the 2006 Notices article give Venn 1880 as volume 9, copying a misprint in the footer of its first page; it is volume 10. Henderson's 1963 note does claim a symmetric 7-Venn diagram ("A symmetric Venn diagram for seven classes has been found, the regions being irregular hexagons"), which was never shown and later lost. Schröder (1877), Macfarlane (1879) and Scheffler (1880) drew two-circle frames before Venn; Venn's new step was using them to express propositions. Not read: Grünbaum's "Venn diagrams II" (1992) itself (its contents come from Edwards's Cogwheels and the survey), Edwards 1994 (the first publication of Hamilton, per Cogwheels), and Hamburger and Pippert 2000 (paywalled; it may or may not quote Dunham).

## Notes from the third session (Opus, 2026-10-07 and 08, VS Code on dreeves's Mac)

n = 23 is drawn: venn23-c25-s230025, the one of Dzoba's six 23-curve certs verified in Lean 4. `venn.py certs` downloads it from the v1.3 release of dzoba/venn17 (gzipped, 103 MB) and unzips it to certs/venn-23.json (889 MB), checking the SHA-256 that the README there publishes for the unzipped JSON. What 23 took, which every plotter n now goes through:
* cert.py reads a cert at a fixed stride instead of with json.loads (7 s at 23) and builds the crossing graph in numpy arrays (cert.Primal), in place of the vendored plotter_svg.Primal, whose Python objects take 2 GB at 19 and would take about 30 at 23. qual_crossing_graph checks it against the vendored one, crossing for crossing; qual_cert_read checks the reader against json.loads. It numbers crossings in the cert's order, so the drawings no longer depend on PYTHONHASHSEED: they are byte-reproducible (qual_svg_reproducible, for n up to 13).
* Everything after the layout is done for curve 0 alone: its knots, its smoothing, and its check, offenders(). write_svg() writes curve 0 and the turned uses directly, for the conics too (compact(), matched(), stored() and ROUNDING are gone; the conics have six decimals now). Curve i is curve 0 turned by turn(s i, n) degrees, s the crossing graph's shift (1 for the conics); the checks turn curve 0 by exactly the degrees the file states.
* Crossings are counted exactly: crossings.py certifies each crossing of the drawn cubics, and each place without one, instead of sampling the curves as polylines. Sampling (median chord / 6) had missed crossings where two curves run within about 0.1 unit of each other near a knot: the drawings committed before this had 131,104 crossings at 17 (the cert: 131,070), 525,464 at 19 (524,286) and 8,423,106 at 23 (8,388,606), plus 69 tiny loops of curves at 23, and the sampled quals passed them all. Three independent exact counters agreed on those numbers; the one kept (a workflow agent's, judged by a skeptic with an exact rational verifier) checks curve 0 against each copy d = 0 .. n // 2, so each orbit of crossings is found once and no sectors are needed (the sectors, and their trouble at sector edges, are gone). Where it can certify neither a crossing nor its absence it reports a contact, which fails the drawing; see its docstring for what causes one. Both offenders() and drawn_faces() (qual_svg_matches_cert) use it; geom.py is down to cross2, nets and rotate. 17, 19 and 23 were redrawn with it: smoothing flagged 292, 40, 9 and 0 orbits at 17, 3,023, 512, 15 and 0 at 19, and 53,523, 10,490, 1,130, 34 and 0 at 23.
* radial_warp's aniso is 1, not the plotter's 1.8 (dreeves agreed, 2026-10-07). At 1.8 the straight-arc drawing of 23 crossed itself in every sector: along one short arc the warp's slope falls from 1.8 to 1.3, which carries a crossing 1e-5 away over to the arc's other side. At 1 the warp scales every crossing but the outer n by one factor, so the straight-arc drawing keeps the Tutte layout's planarity at any n. The cost is looks: the band of crossings is about 40% narrower than at 1.8 (17 to 23) and the median spacing of crossings 26% smaller, though they cross at wider angles. The alternative offered was 1.4 (a band 20% narrower than at 1.8).
* quals.py's cert check runs at 23 (numpy orient() and single_rotation_cycles(), the latter returning False where the old dict walk raised KeyError).
* view.html draws 23 on a canvas and every other n as SVG paths, as before (dreeves chose this, 2026-10-07, over a canvas for every n): `const renderer = n === 23 ? canvasRenderer() : svgRenderer()`, everything else shared. A worker (canvas.js) parses the file's bytes strictly, cuts curve 0 into a 64 by 64 grid of Path2Ds, and draws each view on an OffscreenCanvas in batches, culling cells out of view; the page shows each finished bitmap, moved by #picture's transform during gestures like the SVG. Measured at 23 on a loaded machine: first drawing 1.4 s (Chromium), 3 to 4 s (WebKit, Firefox); redraws at fit 1 to 2.6 s, zoomed in 0.6 s down to 5 ms. The canvas path's quals (qual_viewer_canvas_*) compare the canvas with a reference the check draws itself from the file ("matches"); the SVG path's quals are unchanged and run on 2 to 19. PNG_ONLY and qual_png_only are gone.
* No child process for the layout: the numpy crossing graph is freed when plotter_layout returns.

Numbers at 23: drawing it took 46 minutes wall (24 of them the layout) and 26 of CPU, with swap at 20-26 GB from other work, peak footprint about 4 GB; qual_cert_valid, qual_svg_matches_cert, qual_svg_defects, qual_png_matches_svg and qual_svg_symmetric together take 6 minutes, crossings() alone about 40 CPU-seconds and 2 GB.

Things that may trip up the next instance:
* Canvas line widths: a 2D canvas strokes lines under about 0.9 of its own pixels fast, wider ones far slower (23 at 2560 by 1440, 2 device pixels to a CSS pixel: 11 s in Chromium, 38 in Firefox, 52-62 in WebKit, which then showed nothing). So canvas.js gives its canvas fewer pixels than the screen when lines would be wider than 0.85 of them; the lines look a little softer. That cliff is why the SVG viewer stays for 2 to 19: a canvas made 19 13 s a redraw in WebKit at 1728 by 1000 against the SVG's 0.2 s.
* smooth() no longer asserts first that the drawing with every arc straight is clean: at 23 it isn't certifiable, because at six orbits one curve turns back at a crossing in a hairpin a few tenths of a degree wide while another passes through it, and crossings() can't certify that as a pair of straight corners, though it can once smoothed, and smoothing never needs those arcs straight. smooth()'s own assert after eight attempts stands.
* At 23 the closest approach between arcs that share no crossing is 2.3e-5 page units, set by the Tutte layout's tight bundles whatever the warp. Rounding to six decimals and turning can put the two copies of a crossing 1.4e-6 apart, so the margin is about 16 times; five decimals would leave about 1.6.
* offenders()'s rule for a knot crossed other than once has no constructed case in the quals (building one means two curves within a fraction of a unit near a knot, on the spans next to it); qual_svg_matches_cert catches the result in a drawing either way.
* The browser quals take about 5 minutes with 23 in them, and their timing checks (qual_viewer_slow, qual_viewer_canvas_frames) can fail when the machine is loaded with other work; run them alone before believing such a failure.

## Notes from the fourth session (Opus, 2026-10-08, workflow agents on dreeves's Mac)

The viewer shades a region (the feature request README.md held until 80056e9; dreeves's decisions of 2026-10-08): a checkbox per curve, under its swatch (beside it where the swatches stand in a column), all unchecked on opening; the region inside the curves checked and outside the rest is shaded in site.css's --line, beneath the curves, with nothing checked the region outside every curve. The swatches are also a slider's stops (drag along them; arrow keys, Home and End on a focused swatch). The turn button (its face τ/n, with n's value: τ/7; in the top bar) turns the shading 1/n of a full turn anticlockwise about the page's centre (#region's WAAPI animation), then checks the curves the checked ones land on (landing(), from the file's angles) and drops the turn once that shading is drawn. Clicks queue up (turning, a chain of promises): one during a turn makes another turn after it, so the button is never disabled during a turn (disabling it dropped the focus, and Enter pressed twice turned once). It is disabled, and greyed out (.icon:disabled, --muted), only until the drawing has arrived (dreeves, 2026-10-09). A turn that fails shows the error, and no turn is made after it (turning.catch(failed)). Quals: qual_viewer_shading, _checks, _slider, _turn, _follow, _download, _error, _phone, _loading, _resize, _canvas_shading, _canvas_turn, _canvas_error, and qual_canvas_outline (canvas.js's outline() in node, without a browser); quals.py's docstring defines shading, probe and turn.

How it's drawn: the worker, canvas.js, draws the shading for every n, on a canvas of its own in #region (z-index -1, after the curves in the document, so #stage's first SVG and first canvas are the curves'); for 23 it draws the curves too, as before. view.html's painter() is that worker and its two canvases; svgRenderer() and canvasRenderer() each make one (k = -1: no curves). The page fetches the SVG, once, for every n (fetched()), and hands the bytes over to the worker (send(), a transfer); the worker takes its first message for them and every later one for a view, so painter() posts no view before them. For SVG paths the page decodes the text first. (When the worker fetched the file itself, 2 to 19 were downloaded twice: 4.2 MB more at 19.) A checkbox asks the worker for its drawings alone (the painter's redraw()): the page's redraw() also sets the SVG's viewBox, and so drew 19 anew, 0.2 s a click in WebKit. The shading is --line all over, then for each curve a fill with destination-in (checked) or destination-out (unchecked) of the curve's outline(): exact where it meets the view, each run of spans whose box misses the view or that strays under half a pixel from its chord replaced by the chord (tree() holds the runs' boxes and a bound on their flatness). So the shading's edge may stray up to a pixel from a curve, plus its antialiasing.

Things that may trip up the next instance:
* The viewer reads every n's SVG strictly (canvas.js's parse()), so it needs a server that serves files untouched, such as `python3 -m http.server`. VS Code's Live Server injects a script before </svg>, and then every n fails: `Couldn't load img/venn-07.svg (4674: "!-- Code injected by liv" ≠ "/svg>\n")`.
* WebKit's canvas fills grow much faster than their edges: curve 0 of 23 at fit in a 1200 by 800 window took 7 s as the polygon of its 729,449 knots, 0.72 s of every 4th knot, 87 ms of every 16th (Chromium 52, 20, 8 ms). Filling whole curves made a drawing of 23 take WebKit 109 s at fit. outline() keeps fills to about 42,000 lines a curve at fit and 8,700 zoomed in by 16.
* The SVG way (a clip path for each checked curve, a mask of the unchecked) made a redraw of 19 take the page's own thread 1.1 to 2.9 times as long in Chromium, 1.2 to 7.8 in WebKit (5.8 at fit with nothing checked: the mask) and 1.7 to 4.9 in Firefox (worst with all checked: the clip paths), on a machine with a load average over 100; that is why the worker draws the shading for every n.
* drawnSince() takes the first drawing shown after the last ask for that ask's. With several asks in a row, a drawing the worker posted before it saw the last one can arrive after it, so the quals' check() sets all but one checkbox without events and clicks the last. view.html's shade() avoids the same race with the asks' numbers (seq).
* Probes are found by the quals' own geometry (label(), a tree like canvas.js's), at least half a line's width plus 1.5 pixels (NEAR) from every curve's centreline, and 6 pixels clear of the box of everything outside the stage that takes the pointer (controlBoxes(); elementFromPoint() at 9 points around each point of a 2-pixel grid took Firefox 34 s). label() judges nearness by the Euclidean distance to pieces of a span under far / 16 across: with the box test it used before (each axis within far) and pieces under far / 4, it took points up to 1.4 times far away for near ones, and no probe fell where the errors below were. Screenshots are decoded by png() in browser_quals.mjs.
* NEAR was measured (screenshots labelled pixel by pixel against the file's curves; the scratch tools aren't committed): in all three browsers, at n = 3, 5, 7, 13 and 23, at fit and zoomed in by 4 or 64, the shading was never wrong further than 1.08 pixels beyond a line's edge (WebKit, n = 13), elsewhere 0.93 at most, so probes are 0.42 pixel clear of that. With the shading's canvas at a quarter of its resolution it was wrong up to 2.1 to 2.7 pixels beyond at n = 7, 13 and 23 (qual_viewer_shading, _checks and _canvas_shading fail); with outline()'s tolerance at 4 pixels instead of half of one, up to 1.3 (n = 7), 1.6 (23) and 1.8 (13), so only qual_viewer_shading's look at 13, with probes every 2 pixels (FINE), fails.
* qual_viewer_shading's covered() pixels: at n = 3 the lines (2.8 pixels wide at fit in a 1200 by 800 window) cover whole pixels, which keep their curve's colour beside the shaded region. With the shading over the curves (#region without z-index: -1) 93 to 97% of them didn't; probes, which keep away from the lines, never noticed.
* turns() logs every frame, ask for a drawing and drawing shown (wrapping Worker.prototype.postMessage and ImageBitmapRenderingContext.prototype.transferFromImageBitmap), and turnedWell() expects the shading turned by exactly -360/n from each turn's ask, when the checkboxes have just changed, until its drawing is shown. With spin.cancel() before await shade(), or without fill: 'forwards', the old set showed unturned meanwhile; the turn quals passed both until they looked at the ask.

* With Google Fonts blocked, as in the quals, Firefox drew τ a whole em (18.4 pixels) wide: a missing glyph's box. Fix round (2026-10-09), on three verifiers' findings:
* Errors: canvas.js's onmessage catches what draw() throws before its first batch and posts it, as it posts a file it can't read; for each view after a file it couldn't read, that's the file's error again, so no rejection is left uncaught. qual_viewer_canvas_error counts uncaught errors, which each engine reports differently for a worker: Chromium as a page error, WebKit as "Unhandled Promise Rejection", Firefox as "[JavaScript Error: ...]". An error in a batch reaches the page as the worker's error event; when canvas.js itself can't be loaded that event has no message, so the error gives its type: "(canvas.js: error)".
* A window of no pixels (Chromium, Firefox; WebKit's Playwright refuses one) gave the canvases none, and drawImage() threw; windows of 1 pixel were fine. Canvases are at least a pixel each way.
* holdable() in browser_quals.mjs holds the worker's messages back: qual_viewer_turn has a drawing asked for before a turn's arrive after the turn's own ask, which must leave #region turned (shade()'s seq). qual_viewer_follow also samples the shading's canvas as the curves are drawn anew, with a MutationObserver on #picture's style, whose callback runs before the worker's next message can: in Chromium the new shading arrived within one 5-ms poll, so a misplaced old one went unseen.
* turns() logs #picture's transform and the boxes of the SVG, its paths and the curves' canvas at every entry, and turnedWell() requires them unchanged ("while the curves stay as they are"); spinning the SVG with the shading passed before.
